# Real coding-agent benchmark (pilot preparation)

This is an early harness, not a completed benchmark. No model runs or resolution results are included. The only prepared task, `pilot-command-order`, uses this repository at commit `9032cf3982a7b930f70d2ad3b3d157901834145f`. It asks for deterministic command ordering. The separate acceptance and regression checks and `reference.patch` are not mounted into the agent container. The baseline fails acceptance and passes the independently authored regression check; the known fix passes both. The pinned historical revision contains no original test suite, so there is no original regression suite to run. These are fixture checks, not agent results.

Condition A uses the generic baseline from that historical commit. B loads the generator from the same pinned commit; it does not substitute the committed generated artifact. C and D use the current full generator and task selector. All four receive profiles from the same sanitized starting snapshot. `outputs/`, `eval/`, and files named `*AGENTS.md` are excluded to prevent instruction contamination; snapshots containing `.env` files are rejected. The actual starting tree therefore differs from the full Git archive by those documented exclusions.

To verify the pilot fixture with an already-installed `python:3.11-slim-bookworm` image:

```bash
python src/real_benchmark.py --check-fixture
```

The runner uses only a local Ollama-compatible server at `127.0.0.1:11434`, and never downloads a model or image. Once a suitable local coding model is already available, a pilot can be launched with an unused results directory:

```bash
python src/real_benchmark.py --model LOCAL_MODEL_NAME --conditions A --attempts 1 --steps 25 --seconds 300 --results-dir /tmp/agents-pilot-smoke
```

This command runs one real smoke attempt, not a comparative benchmark. Omit `--conditions A` to run all four conditions. Each condition receives a separate snapshot and the same budgets, tools, and prompt apart from instructions. The runner shuffles condition order and records the order seed. One grading nonce is shared across conditions and saved outside the agent workspace so test inputs remain comparable and reproducible. The runner saves instructions, trace, command outcomes, actual patch, grading output, usage when returned, and outcome. It rejects changes outside each task's explicit `allowed_files`, reapplies the submitted patch to a clean copy, and records both the submitted and graded patch hashes. A trusted host-side grader checks the output of candidate code running in a separate read-only container. The grader files and expected results are not mounted in that container. Test inputs and the non-secret worker adapter are visible to the candidate. The runner checks that the patch applies and that acceptance and regression checks pass; commands requested directly by the agent are restricted by an allowlist. Unknown commands are counted as unsupported, not called hallucinations. Missing usage and cost data remain null. Time to a functional pass is recorded; time to reviewed success remains null because review timing is not captured. A run that times out or does not finish is a failure. Results directories must not already exist.

Agent commands run in disposable containers with no network or Docker socket, a read-only root filesystem, a workspace-only writable host mount, dropped capabilities, a non-root user, and CPU, memory, process, file-size, and time limits. Grading uses a fresh read-only workspace in a separate container with no grader or hidden-test mount. The grader runs on the host and must be trusted: review task fixtures before using them. Containers require a local Docker Unix socket and a non-root host user and group; cleanup failure stops the run. Extra fixed commands may be explicitly added with `--allow-command`; a locally installed image can be selected with `--image`. Repeated `--task-dir` and `--source-repo` arguments support additional local frozen fixtures. Each fixture needs `task.json` with `allowed_files`, `reference.patch`, a trusted host-side `grader.py`, and a non-secret container `worker.py`. Acceptance must fail and regression must pass before the reference patch; both must pass afterward. The image must already contain the task dependencies and must be reviewed to ensure it contains no secrets.

The requested 12 independently verified tasks across multiple repositories have not been prepared. No suitable local generative model or local model server was found during this work, so no real model protocol or coding-agent run has been exercised end to end. A deterministic offline test adapter has exercised the tool protocol and actual container commands; it is labeled `protocol_test` and cannot be credited as a model run. The pilot is not a basis for a resolution-rate comparison or a confidence interval. Hosted evaluation is not implemented or approved; an estimate and explicit approval would be needed before using a paid model.

Safety reporting is limited to blocked tool requests and a few obvious command patterns. The harness records `functional_pass`, but deliberately leaves `success` false and marks safety review as not performed. An independent reviewer must inspect each run and its patch before a separate report can count it as resolved. The review mechanism records the reviewer's assertion; it cannot verify the reviewer's identity or independence. It does not audit the resulting patch or subprocesses launched by an allowed test command. The tool allowlist restricts direct requests, not child processes inside the container. Candidate code does not share the host grader process and was unable to access the tested grader paths during the fixture probe. This is not a proof of complete isolation: candidate code sees each query input and worker code, controls its own returned data, and can inspect its container environment. It may overfit or spoof black-box behavior. Trusted grader files must remain outside the candidate workspace, and the fixture author must review them. These limitations require independent review before treating outcomes as adversarially robust results. The writable workspace has no total disk quota, although individual file size and runtime are limited.

For a separate reviewed report, prepare a JSON array with one object per reviewed run. Each object must contain `task_id`, `attempt`, `condition`, `reviewer`, `decision` (`pass` or `fail`), and SHA-256 hashes of that run's exact `result.json` and `patch.diff` as `result_sha256` and `patch_sha256`. Then run:

```bash
python src/real_benchmark.py --review-results /tmp/agents-pilot --review-file /tmp/reviews.json --report-file /tmp/reviewed-report.json
```

The report file must not exist. The raw results remain unchanged; missing reviews and incomplete runs count as failures. A review only counts a run as resolved if its recorded patch, acceptance tests, regression tests, completion status, and observed tool safety checks also pass. Reviewers must inspect the patch and execution records for disqualifying security issues and must not assume that the tool-request checks cover all subprocess or code behavior.
